A COST NOTE UP FRONT — READ THIS FIRST
--------------------------------------------
Your abstract mentions alerting "such as email or SMS." Email via
Brevo is genuinely free at this project's scale (as in your other
projects). SMS is NOT free the way email is — SMS APIs (Termii,
Twilio, etc.) charge per message, even on their "free trial" tiers
which usually just give you a small number of free trial credits, not
ongoing free sending. Recommended design: email is the ALWAYS-ON, free
default channel for every alert; SMS is an OPTIONAL channel, only
triggered for the highest severity level (e.g. "critical"), so you
don't burn through paid credits during routine testing/demoing. State
this cost-consciousness explicitly in your report — it's a sensible,
real-world engineering decision, not a limitation to hide.

PING/ICMP CAVEAT — READ THIS FIRST
----------------------------------------
True ICMP ping typically requires raw sockets and elevated OS
permissions, which are often unavailable or blocked inside a
containerized hosting environment like Render. Rather than fighting
this, use a TCP CONNECT CHECK (attempt to open a TCP connection to the
target host/port using Node's built-in `net` module, measure whether
it succeeds and how long it took) as your "ping test" — this is a
legitimate, widely-used substitute for basic reachability testing in
real monitoring tools when ICMP isn't available, and it's honest to
call it exactly that in your report: "a TCP connect check used in
place of raw ICMP ping, since ICMP requires elevated privileges not
available in typical cloud hosting environments." Don't claim it's
literal ICMP ping if it isn't.

SCHEDULING DESIGN — WHY NOT JUST ONE GLOBAL node-cron JOB
----------------------------------------------------------------
Different services will have different check intervals (e.g. a
critical payment API checked every 30 seconds, a low-priority internal
tool checked every 5 minutes). Rather than one crude fixed-interval
cron job scanning everything every time, implement a lightweight
in-process scheduler:
  - On startup (and whenever a service is created/updated), (re)schedule
    that service's own check loop using `setInterval` (cleared and
    recreated if the service's interval changes), OR use `node-cron`
    with a single "tick every N seconds" job that checks which
    services are due for a check based on their `lastCheckedAt` +
    `checkIntervalSeconds`
  - Either approach is fine — document which you chose and why in
    Chapter 3. The per-service `setInterval` approach is simpler to
    reason about for a final year project scope; a job-queue-based
    approach (e.g. BullMQ + Redis) is more production-grade but adds
    real infrastructure complexity you likely don't need here

CORE FEATURES — COVER EVERY SCENARIO BELOW
----------------------------------------------

1. SERVICE REGISTRATION & CONFIGURATION
   - Admin/manager registers a service to monitor: name, check type,
     target URL/host/port, expected status codes, interval, timeout,
     degraded-response-time threshold, failure/success thresholds,
     severity level, optional API-health auth header (encrypted at
     rest), optional SSL expiry monitoring
   - Editing a service's `checkIntervalSeconds` must actually
     reschedule its running check timer, not just update the DB field
     and leave the old interval running until a server restart
   - Deactivating a service pauses checks without deleting historical
     data

2. THE CHECK ENGINE (get this working standalone first)
   - `httpCheck.js`: makes an HTTP/HTTPS request to the target,
     records status code, response time, and whether the status code
     matches `expectedStatusCodes`
   - `tcpCheck.js`: attempts a TCP connection to host:port within the
     configured timeout, records success/failure and connect time —
     your "ping" substitute, per the caveat above
   - `apiHealthCheck.js`: hits a specific health endpoint, optionally
     attaching a decrypted auth header, and validates the response
     body against an expected shape (e.g. `{ status: "ok" }`) — a
     200 status code alone isn't enough if the body itself indicates
     an unhealthy state
   - `sslCheck.js`: for HTTPS targets with `sslCheckEnabled`, inspects
     the certificate's expiry date (Node's `tls` module can retrieve
     peer certificate details) and flags it if within
     `sslExpiryWarningDays` of expiring, or if the certificate is
     already invalid/expired — a genuinely useful, easy-to-demo extra
     feature for a "cloud service monitoring" project
   - Every check attempt (success or failure) is recorded as a
     `checkResults` document, regardless of whether it triggers an
     incident
   - On a failing check, retry once or twice with a short delay before
     counting it as a definitive failure — reduces false alarms from
     genuinely transient network blips, distinct from the
     consecutive-FAILED-CHECKS threshold used for incident creation

3. INCIDENT DETECTION & LIFECYCLE (incidentService.js)
   - A service's `consecutiveFailureCount` increments on each failed
     check (after the retry logic above has run) and resets to 0 on
     any successful check
   - When `consecutiveFailureCount` reaches the service's configured
     `consecutiveFailuresForIncident` threshold AND no incident is
     currently open for that service, open a new incident (status
     "open", severity copied from the service's current
     `severityLevel`, `detectedAt` = now, first timeline entry
     "opened")
   - While an incident is open, continued failing checks do NOT open
     duplicate incidents — check the "is there already an open
     incident for this service" condition (via the compound index)
     before creating a new one
   - When `consecutiveSuccessCount` reaches
     `consecutiveSuccessesForResolve` while an incident is open,
     auto-resolve it: status "resolved", `resolvedAt` = now,
     `downtimeDurationSeconds` computed from `detectedAt` to
     `resolvedAt`, timeline entry "resolved"
   - An admin/manager/responder can manually "acknowledge" an open
     incident (records who and when) — acknowledgment doesn't resolve
     it, just signals "someone is on it," which matters for escalation
     logic below
   - FLAPPING DETECTION: if a service opens and auto-resolves several
     incidents within a short rolling window (e.g. 3+ incidents in 15
     minutes), mark the service's `currentStatus` as "flapping" and
     open a SINGLE incident describing the flapping pattern rather
     than a rapid-fire sequence of separate open/resolve incidents —
     this avoids an alert storm and is a realistic, examinable design
     choice worth explaining

4. ALERTING (alertService.js)
   - On incident OPEN: email every user whose `notificationPreferences`
     opt them in, via Brevo; additionally send SMS to users with
     `smsEnabled: true` AND whose `smsMinSeverity` threshold is met by
     this incident's severity (i.e. SMS only for the incidents that
     matter enough to justify the per-message cost, per the COST NOTE)
   - ESCALATION: if an open incident hasn't been acknowledged within a
     configurable window (e.g. 10 minutes), send a follow-up
     escalation alert (email, and SMS if the severity qualifies) to a
     broader distribution list or a designated secondary contact —
     implement this as a check within the scheduler tick or a
     dedicated `node-cron` job scanning for unacknowledged incidents
     past their escalation window
   - Every alert attempt (successful or failed) recorded in
     `notificationLogs` — this collection exists specifically so you
     can answer "why didn't I get notified" during testing/demo, which
     WILL come up
   - Alert sending failures (Brevo/SMS API errors) must not crash the
     incident-detection flow — log the failure, keep the incident
     record correct regardless of whether the notification succeeded

5. MAINTENANCE WINDOWS
   - Admin can schedule a maintenance window for a service (start/end
     time, reason)
   - While a service's active maintenance window is in effect, failed
     checks during that period are still RECORDED (for completeness)
     but do NOT increment `consecutiveFailureCount` toward opening an
     incident, and the service's `currentStatus` shows "maintenance"
     rather than "down" — this is a standard, expected feature of any
     real monitoring tool and prevents false alarms during planned
     downtime

6. SLA / UPTIME REPORTING (slaService.js)
   - Compute uptime percentage per service over selectable periods
     (24h/7d/30d/custom range) from `checkResults` (successful checks
     / total checks in the period) AND from incident downtime
     duration (two related but distinct calculations — document which
     one you present as the headline "uptime %" and why)
   - Compare against a configurable SLA target (e.g. 99.9%) per
     service and flag periods where it was breached
   - Historical response-time trend chart per service (recharts)

7. DASHBOARD (real-time via Socket.io)
   - Service overview grid: every monitored service, current status
     (color-coded: up/degraded/down/flapping/maintenance), last
     checked time, updated live as new check results arrive
   - Incident list: active incidents prominently surfaced, filterable
     history of resolved incidents, each showing its full timeline
   - Service detail view: response-time and uptime charts, recent
     check history, SSL expiry status if enabled
   - SLA/uptime report view: per-service uptime % over selectable
     periods, SLA breach flags
   - Admin: manage services, maintenance windows, users/notification
     preferences

8. OPTIONAL — PUBLIC STATUS PAGE
   - A simple, unauthenticated public page showing current status of
     selected services (admin chooses which services are
     "public-facing") and a recent incident history — a genuinely
     standard feature of real status-monitoring products (Statuspage,
     UptimeRobot, etc.) and an easy, impressive extra for your defense
     if you have time for it

EDGE CASES TO EXPLICITLY HANDLE
------------------------------------
  - A service's `severityLevel` is changed by an admin WHILE an
    incident for that service is already open -> the OPEN incident
    keeps its originally-snapshotted severity (don't retroactively
    change an in-progress incident's severity just because the
    service's default changed later) — this is why severity is copied
    onto the incident document at creation time, not looked up live
    from the service every time it's displayed
  - Two checks for the same service overlap (a slow check hasn't
    returned before the next scheduled check fires) -> guard against
    concurrent overlapping checks for the same service (e.g. a simple
    "is a check currently in flight for this service" flag) so you
    don't get duplicate/racing check results
  - A service is deleted while it has open incidents or historical
    check data -> block deletion (or require resolving open incidents
    first / soft-delete/archive) rather than silently orphaning
    incident records
  - Maintenance window ends WHILE the service is still actually down
    for a real reason (maintenance ran long, or a real problem
    emerged independently) -> once the window ends, resume normal
    incident-detection logic immediately; don't require manual
    re-activation
  - SSL certificate check itself fails (can't connect to check the
    cert at all) -> distinguish this from "certificate is expired" as
    a different error type/incident, since one means "server
    unreachable" and the other means "server reachable but cert is a
    problem" — different remediation paths
  - Flapping detection window itself needs a cooldown — once flagged
    "flapping," don't immediately re-flag it again on the very next
    check cycle; require the service to stabilize (a sustained period
    of consistent status) before flapping status clears
  - A user's `notificationPreferences.smsEnabled` is true but no valid
    `phoneNumber` is set -> skip SMS for that user with a logged
    reason in `notificationLogs`, don't let a missing phone number
    silently swallow the alert attempt without a trace
  - Brevo or the SMS provider is down/rate-limited during an incident
    storm -> alert sending failures must be logged and retried
    (or at minimum clearly reported), never allowed to crash the
    check/incident pipeline itself
  - Very high-frequency checks (e.g. a 10-second interval on many
    services) generating a large `checkResults` volume -> see DATA
    RETENTION below

DATA RETENTION
-------------------
Raw check results at even a modest interval (e.g. every 60 seconds
across a dozen services) accumulate quickly. Either:
  a. Set a MongoDB TTL index on `checkResults.checkedAt` to
     auto-expire raw results after a defined window (e.g. 30-60 days),
     OR
  b. Run a scheduled aggregation job that rolls up older raw results
     into hourly/daily summary documents (uptime %, avg response time)
     in a separate collection, then prunes the raw detail
Pick one, implement it, and document the tradeoff explicitly in
Chapter 3 — the same scalability-awareness talking point as any
high-frequency time-series monitoring system.

- The consecutive-failure/success threshold logic (never opening or
  resolving an incident on a single blip) and the flapping-detection
  cooldown are your strongest, most examinable pieces of design —
  they're what separates a genuinely useful monitoring system from one
  that spams false alerts constantly.
- The severity-snapshotted-onto-the-incident-at-creation-time design
  (rather than looking it up live from the service every time) is a
  small but real data-integrity decision worth explaining if asked.
- Be upfront that your "ping" check is a TCP connect check, not literal
  ICMP, and explain why (container/hosting environment permission
  constraints) — this is honest engineering, not a shortcut to hide.
- The email-always/SMS-critical-only alerting design is a deliberate,
  sensible cost-control decision — say so explicitly rather than
  looking like SMS support was simply incomplete.
